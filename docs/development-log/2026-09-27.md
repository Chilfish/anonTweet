## 修复文章型推文（X Article）返回空链接 → 富文本块文档 + 独立阅读页（✅ 已完成）

**背景**：`https://x.com/bang_dream_on/article/2104058634452005231` 经 `GET /api/tweet/get/...`
只返回一条指向文章页的裸链接（`text` = `https://t.co/EhcNsbMwRz`），标题与正文全丢。

**先核实上游返回了什么**（临时脚本直连 `TweetResultByRestId`）：推文响应里**其实带**
`article.article_results.result`，`rest_id`/`title`/`preview_text` 都有，唯独缺 `plain_text` 全文。

**根因两层**：

1. **请求侧**：全文需 `fieldToggles.withArticlePlainText = true`，`details()` 没带；且按 `User.ts`
   的**对象**写法会被 axios 序列化成 `fieldToggles[withArticlePlainText]=true`（实测 `axios.getUri`），
   而 X 只认 `fieldToggles={"withArticlePlainText":true}` 这种 JSON 字符串。
2. **解析/渲染侧**：`enrichTweet` 从未读取 `article` 节点。

**进一步实测发现富文本是现成的**：`replies()` 早已带 `withArticleRichContentState:true`，`details()`
补同款 toggle 即可拿到 Draft.js `content_state`（`blocks[]` + `entityMap[]`）。且「表格/代码」其实是
`MARKDOWN` 实体里的 GFM（样例 `2099885132379500562` 的 entity key `5` 就是一张 Markdown 表格）——
X 并无 table/code 块类型。详见 [`docs/features/tweet/article.md`](../features/tweet/article.md) §2。

**实现**（全部未提交，仍在工作区）：

- 请求：`requests/Tweet.ts` `details()` 补 `fieldToggles = {withArticleRichContentState:true, withArticlePlainText:true}`
- 类型：`Details.ts` 扩 `article` 原始节点（`RawArticle*`）+ `app/types/article.ts`（`TweetArticle`/`ArticleBlock`/`ArticleRun`/`ArticleMedia`）
- 解析（纯函数）：`app/lib/article/parse.ts` `parseContentState`（entityMap 数组/Record 双形态、未知块降级、mention/hashtag span、行内样式）
- 映射：`lib/react-tweet/utils/article.ts` `mapArticle` + `resolveArticleLink`（无富文本路径的仅链接入口）
- 挂载/回填：`parseTweet.ts` 产出 `article`；`getTweet.server.ts` 回填判据改 `format==='rich'`
- 渲染：`app/components/article/*`（`ArticleBody`/`ArticleRuns`/`ArticleMarkdown`/`ArticleImage`/`ArticleEmbedTweet`）
  - `TweetArticleCard` 紧凑卡 + 新依赖 `react-markdown` + `remark-gfm`
- 路由：`app/routes/article.tsx` + `/article/:id`（阅读页）；`PlainTweet` 补挂卡片；`tweet-body` 去重链接

**验证**：新增 `test/unit/article-parse.spec.ts`（fixture 驱动）、`test/acceptance/article-render.spec.ts`；
更新 `test/unit/{article,getLocalTweet}.spec.ts`；AC-tweet.md v1.4（AC-TWEET-014/015/016）。
`bun run typecheck` / `lint` / `test`（469 passed）全绿。**本地实测**：`/api/tweet/get/2103576349499855160`
返回 `format=rich`、81 块（11 heading / 7 image / 13 list-item / 50 paragraph）+ 封面；
`/article/2103576349499855160` SSR 200。

## 修复文章行内加粗整段误应用（owner 反馈 `status/2103463356913098908`）

**现象**：`https://x.com/bang_dream_on/status/2103463356913098908` 的正文里只有段首短句该加粗，
实际整段（乃至全文）都渲染成粗体。

**定位（真机上游数据）**：该文 `content_state` 无任何 entity/mention，`inlineStyleRanges` 形如
`{offset:0,length:15,style:"Bold"}`——只覆盖段首。而 `buildRuns` 只在 LINK/mention/hashtag 边界切分，
无 span 时整块成为一个 run，`stylesFor` 的「区间有重叠即命中」判断就把 Bold 应用到整段。

**修复**：`buildRuns` 改为按「实体边界 ∪ 样式边界」切分（Draft.js 语义），每段用
`stylesInRange` 取**恰好覆盖**它的样式；样式区间与实体同样参与切分。加粗范围因此精确到区间。

**回归**：新增真实 fixture `test/fixtures/articles/2103463356913098908.json`（21 块，纯段落 + 段首 Bold），
`AC-TWEET-014` 增用例断言 `b0tca` 块仅首行加粗、其余不加粗；`verify --ac AC-TWEET-014` 覆盖。

**踩坑**：Draft.js run 的切分点是样式 ∪ 实体，不是只看实体；「区间有重叠」是错判据。

## 文章翻译线上 500：模型吐出非法 JSON（owner 反馈 `/api/ai-translation`）

**现象**：线上 `/api/ai-translation`（`type:'article'`）返回 500，`aiError.type = AI_NoObjectGeneratedError`、
message = `No object generated: could not parse the response.`，前端只会看到泛化的「Translation failed」。

**复现（真实端点，非推测）**：拿 owner 给的请求体（`deepseek-flash` / `thinkingLevel:minimal` / 该篇日文文章）
直连 `api.deepseek.com`，在 provider 的 `fetch` 上打印请求与响应。3/3 稳定失败：

- 请求确实带了 `response_format: {"type":"json_object"}`（`max_tokens` 未设），但**没有下发 JSON Schema**：
  `@ai-sdk/openai-compatible` 的 `supportsStructuredOutputs` 默认 `false`，SDK 只告警
  `responseFormat ... only supported with structuredOutputs`，zod schema 从未到达模型。
- 模型 `finish_reason=stop`、1286 字符、**没有截断**，但输出结构非法：`blocks` 里每个块后面都多一个 `}`，
  括号扫描最终 depth = -5（`{"blocks":{"bghfm":"…"},"c2rh5":"…"}…`）。
- `Output.object` 在 `parse-and-validate-object-result.ts:34` 抛 `AI_NoObjectGeneratedError`。

**为什么必然炸**：`translateBatch` 的 2 次重试只针对占位符不匹配，`generateText` 一抛错就跳出循环并冒泡，
整篇 500；`normalizeAIError` 又只留 `type`/`message`，把 `text`/`finishReason` 丢掉，线上无从定位。

**修复**（`app/lib/article/translate.ts`）：

- 输入从 `[{key,text}]` 数组改为 `{ 块key: 原文 }` 对象，与要求的 `blocks` 输出同构；
- system prompt 把「一个 `blocks` 对象含全部 key、禁止中途闭合」写成硬约束，并给出两个 key 的示例；
- `generateText` 包 try/catch：解析失败也走重试（≤2 次），不再中断整篇；
- 单批失败可容忍（保留成功块），但整篇一块都没翻出来时抛错，不以 `success` 返回空译文；
- `normalizeAIError`（`app/lib/ai-error.ts`）对 `NoObjectGeneratedError` 补 `generatedText`（截断 2000）与 `finishReason`。

**验证**：改法先在直连脚本里对照 4 种变体（对象输入 / 强化 prompt / 数组输出 / 单块）均通过；
AC-TWEET-020 用 `ai/test` 的 `MockLanguageModelV4` 驱动**真实** `generateText` + `Output.object`，覆盖
「解析失败重试 / 部分成功保留 / 全失败显式报错 / 送入模型的输入形态」；把修复反向改掉时其中 3 条用例确实变红。
`test` 490 passed、`typecheck`/`lint` 绿、`verify --ac AC-TWEET-020` 4 passed。

**踩坑**：

- vitest 会把 `vi.fn()` 实现里抛出的错误当作**未处理错误**上报（即使调用方 catch 了），所以「在 mock 里抛错」
  无法用来复现；必须用 `ai/test` 的 Mock 模型驱动真实 `generateText` 才能触发同样的解析失败。
- DeepSeek 的 `json_object` 模式不保证结构正确（本次就是合法 JSON 之外的多余括号），不能当成 schema 约束用。

## AI 失败信息不完善：补实体上下文（owner 反馈）

**现象**：线上 `/api/ai-translation` 失败时响应体只有
`{ success:false, error:'Translation failed', status:500, message, aiError:{type,message} }`——
**没有 tweetId / articleId / igPostId，也没有 model / provider**，无法判断是哪条内容挂了。

**约定（owner 澄清，勿改）**：这些 BFF 端点的 HTTP status **一律 200**，失败与否和失败类别由 body 的
`success` + `status` + `error` 表达。业务逻辑拦截（无效输入、缺 key、baseUrl 不在白名单等）不该在
Vercel 日志里刷成 error，否则真正的网关/上游故障会被淹掉。本次修复**不改变**这条约定。

**修复**：

- `app/lib/ai-error.ts` 新增 `buildAIFailure(error, { errorCode, status?, message?, context? })`：
  产出统一失败 body（`success:false` / `error` / `status` / `message` / `targetId` / `targetType` /
  `model` / `provider` / `aiError`），并落一条 `ai.fail` 结构化日志（targetId 走 `suffix` 摘要）。
  路由侧 `return data(buildAIFailure(...))`，HTTP 仍为 200。
- `ai-translation`（article / ins / twitter）、`ai-vision`（generate / translate / save）、`ai-test`
  全部改用该 helper；4xx 路径补 `targetId` / `targetType`；`model` / `provider` 提到 try 外，
  catch 里才能带上。
- `ig/translate` 也带上同样的上下文（该路由原本就用真实 HTTP status，保持原状）。
- `ai.translate.article.batch` 增加 `targetId`（`autoTranslateArticle` 新增同名选项）。

**顺带修的同类问题（审计后）**——都是「失败在日志里定位不到是哪一条」：

- `api/tweet/search.ts` 的失败路径**此前没有任何日志**，补 `console.error`（含 q / type / cursor）。
- `api/proxy/image.ts` 上游非 2xx 无日志、catch 不带 url，补上。
- `article.tsx` / `tweet.tsx` 的 loader 是裸 `catch {}`，线上页面打不开时**日志里连 id 都没有**，补带 id 的日志。

**验证**：AC-OBS-002（单测 + 集成）。集成用「未知 provider」触发路由 catch（不触网、不需要 key），
断言三分支分别回带 `article.id` / `igPost.id` / `tweet.id_str`，且 `res.status === 200` +
`body.status === 500`（HTTP 200 约定未被破坏）。`test` 493 passed、
`verify --exit-on-fail` 64 文件 / 504 passed / 0 failed、`typecheck`/`lint` 绿；
OpenAPI（`llms.ts` 的 `ErrorResponse` + 三条 AI 500 描述）与 skill 快照已同步。

**遗留（记入 backlog）**：非 AI 路由的错误响应字段不统一（部分缺 `success`、`bili-post` 恒 200、
`tweet/list`/`replies`/`user/get` 无 try/catch），以及 `ig/translate` 用真实 HTTP status 与
「HTTP 200」约定不一致——是否统一待 owner 裁决。

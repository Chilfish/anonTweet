## 版本单源治理：OpenAPI / skill 版本去手写副本

**背景**：版本曾手写在四处，极易漂移——`app/lib/llms.ts`（OpenAPI `info.version: '1.0.0'`，
与 `package.json` 的 `version` 已不一致）、`SKILL.md`（`metadata.version: 1.2.0`）、
`scripts/anon-tweet.ps1`（UA `anon-tweet-skill/1.2`，连格式都与 SKILL.md 不一致）、
随附快照 `references/anon-tweet-openapi.json`（`1.0.0`）。

**结论（两个版本域，各自单源，不合并）**：

- **应用 / API 版本** — 单源 `package.json`。`app/lib/llms.ts` 改为
  `import pkg from '../../package.json'` + `info.version: pkg.version`（本模块仅服务端使用，
  tsc / Vite SSR / Vitest 三处均可解析，无需 vite `define` 全局）。随附快照由 `/openapi.json`
  重新生成对齐，不再手写。
- **skill 版本** — 单源 `SKILL.md` `metadata.version`（第三方安装器读取该字段）。
  `anon-tweet.ps1` 删除 UA 手写副本，新增 `Get-SkillVersion` 运行时从 `../SKILL.md` frontmatter
  读取（找不到文件回退 `unknown`）。**skill 不跟随 `package.json`**：独立分发、独立生命周期，
  证据即本次升级 v1.0.0 → v1.2.0 期间应用仍为 0.1.0；反之应用 patch 也不该向安装方暗示
  skill 契约变更。

**验证**：改动落地当天应用版本由 0.1.0 升至 0.2.1，`/openapi.json` 与随附快照随之变为
0.2.1——单源生效的实证（`package.json` 一处改动，其余自动跟随）。

**门禁**：`test/unit/llms.spec.ts`（AC-LLMS-002）新增两条版本奇偶校验——
`doc.info.version === pkg.version`、随附快照 `info.version === pkg.version`。

**文档**：`release-checklist.md#版本纪律` 由「单源 package.json」更正为两个版本域；
`git-workflow.md#版本发布` 补「重新生成 skill 随附快照」步骤 + skill 版本另算说明。

**同步**：仓库 `.agents/skills/anon-tweet/` 的 `SKILL.md` / `anon-tweet.ps1` / 快照与本地
`~/.agents/skills/anon-tweet/` sha256 全部 MATCH（保持逐字节一致约定）。

**门禁**：`bun run typecheck` ✅；`bun run lint` ✅（0 error/warning）；`bun run test` 368/368 ✅
（+2 新版本校验）；`anon-tweet.ps1 help` 解析运行正常，SKILL.md 版本解析为 `1.2.0`。

## 验证套件诚信审查（`bun run verify/index.ts --exit-on-fail` 到底证明了什么）

**背景**：对 CLAUDE.md / README / CI / pre-push 同时引用的「护城河」命令做一次反向审计——「verify 全绿」
是否等同于「功能被验证」。方法是全量精读 `test/` 三层 + `verify/` CLI 与 AC 契约，并本机实测。

**发现（P1×6 / P2×3，详见 `docs/reviews/review-2026-09-11-test-suite-honesty.md`）**：

- **空跑报绿**：`verify/index.ts` 把 `--ac` / `--module` 映射为 vitest `-t` 子串过滤；无测试名匹配时
  vitest 输出全 `skipped` 并 **exit 0**。实测 `-t AC-TRANS-005`（文档有、测试无）与 `-t AC-NOPE-999`
  均 `366 skipped / exit=0`；`--module translation` / `screenshot` / `postmortem` 均 `368 skipped / exit=0`
  （测试名前缀实为 `AC-TRANS` / `AC-SHOT` / `AC-PM`，与模块名错配）。而 verify help（L47）与这三份
  AC 文档**正是**这样教用户执行的。
- **死断言**：`test/acceptance/ac-sec.spec.ts` L78-79 的 AC-SEC-001「设置页披露」用例开头
  `// 暂时不管他` + `return`，其后 `expect` 全为死代码 → 该 AC 的 P3「披露文案」从未被验证。
- **静态扫描冒充行为验收**：acceptance 层大量 `readFileSync(...).toContain('字面量')`。最刺眼的是
  AC-CI-003 断言 workflow 含 `bun run test`——该字符串只出现在 `.github/workflows/verify.yml` L48 的
  **注释**里，注释即满足。
- **集成层结构性不可失败**：`global-setup.ts` 默认删 `TWEET_KEYS`/`INS_COOKIES` → 正向 AC（TWEET-005/008/010、
  IG-007/008）全员 `skipIf`；AC-SHOT-001/002 用无效 id `__screenshot_verify__` 且只断言「含 HTML」
  （NotFound 页同样满足）；AC-TWEET-006 `catch { return }` 半恒真。
- **门禁命令当前已红**：`bun run verify/index.ts --exit-on-fail` exit 1 —— globalSetup 起的 dev server
  崩在 `TypeError: jsxDEV is not a function` + `ReferenceError: Cannot access 'abort' before initialization`
  （`bun run dev` 单独跑亦 500/退出 1），integration 未执行。
- **AC ↔ 测试名 1:1 断链**：verify/README.md 宣称「AC 编号即测试名，1:1 可追溯」，实测
  `AC-TRANS-002/005/006/007` 只在文档、无 `it('AC-...')` 命名；`AC-TEST-006` 只在测试、不在文档。
- P2：fixture 自证（AC-TWEET-001~004/007、AC-IG-001/002 断言 JSON 自身而非解析器产出，AC-IG-006
  竟不调用 `translateIGCaption`）、AC-TWEET-004 正则恒真、无 `expect-expect` 类 lint 防护。

**结论（不是全盘否定）**：unit 层是真测试（`parseTweet` / `resolveEntities` / `ai-base-url` / `smart-pool`
等有负例与不可变断言）；AC-CARD-002/003 与 `card-render.spec.ts` 是真渲染断言；AC-PM-007 真跑脚本。
问题集中在 acceptance / integration 两层与 CLI 包装层——「全绿」对其中相当一部分不携带信号。

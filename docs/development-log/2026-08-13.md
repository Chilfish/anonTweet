## 弹窗统一收紧 + 设置页 tabs 手机端适配 + Vision 编辑弹窗重写（Apple HIG）

**背景**：连续多轮反馈——「UX 还是丑丑的」→「注意手机端布局，设置页多 tab 溢出」→「padding 很大，tab 很丑」→「图片描述、编辑翻译等等弹窗都很丑」。收敛到两个根因：**弹窗原语 padding 过大** + **tabs 手机端溢出**。中途一度尝试把设置页改 iPhone 式垂直长列表，被用户否回——**tabs 是用户既有导航习惯，保留**（勿为追求 Apple 强行改习惯），溢出改由 tabs.tsx 滑动修复解决。

**弹窗原语收紧（`dialog.tsx`，6 个弹窗一次受益）**：

- `DialogHeader` / `DialogPanel` padding `p-6`（24px）→ **`p-5`**（20px），`DialogFooter` `px-6` → `px-5`——iOS 弹窗边距，24px 是「弹窗都丑」的共病
- 受益弹窗：图片描述 / 编辑翻译（TranslationEditor）/ Alt 翻译 / IG 翻译 / 设置 / 词条

**设置页 tabs（保留 + 手机端修复，`tabs.tsx` / `SettingsPanel.tsx`）**：

- 顺带删除 `SettingsPanel` 从未使用的 `trigger` prop

**Vision 编辑弹窗重写（`AIVisionEditorDialog.tsx`，用户点名「图片描述弹窗丑」）**：

## AI 视觉描述子系统 — 修复：图片 index 映射 + OCR 一图一条目（本 commit）

**背景**：Phase 4 UI 真实联调暴露两个数据正确性问题（用户报告）——

1. **describe 模式**单图推文返回 `"index": 1`（请求 `mediaIndexes: [0]`）——模型不知道图片与
   mediaDetails 索引的对应关系，**自造了序号**，导致 `find(v => v.index === i)` 命中失败，
   描述填不进编辑框、展示块不渲染。根因：`buildVisionMessages` 把 `img.index` 传进参数却
   **从未在消息内容里告诉模型**「第几张图对应哪个 index」。
2. **ocr 模式**单图返回 10 个条目（index 0-9，每行一个对象）——OCR 提示语「逐行提取图片中的
   所有文字」诱导模型**按文字行拆条**，只显示第一个数组值，且无法按图编辑 OCR 结果与翻译。

**修复（三层防御，`app/lib/vision/`）**：

- `messages.ts`：user 内容追加「图片索引映射（…）：0, 2」文本 part，明确告知模型每张图片
  对应的 index、禁止自编序号（describe/ocr 共用）。file part 数不变，AC-005/007 断言不受影响。
- `prompts.ts`：describe/ocr systemPrompt 追加「index 必须使用用户消息中给出的图片索引，
  不得自编序号」；OCR 提示语改为「每张图片只输出一个对象，多行文字合并进 originalText
  （保留原顺序与换行）」，消除按行拆条。
- `parse.ts`：新增 `alignVisionIndexes` 纯函数——结果数量与请求一致时**按序强制重映射**到请求的
  mediaDetails 索引（模型索引不可靠的确定性兜底）；数量不一致（ocr 仍拆条）时保留模型索引，
  交由上层按内容合并。
- `describeImages.ts`：parse 后调用 `alignVisionIndexes(images.map(i => i.index))` 再回填
  provider/model。

**UI 侧零改动**：`resolveVisionView` / 编辑弹窗的 `find(v => v.index === i)` 依赖正确的 index，
修复后命中、可编辑。`updateTweet(tweetId, { visionInfo })` 只写**内存 store**（`tweets`/`mainTweet`，
经 `useTweets` → `displayTweets` → `AIVisionBlock` 刷新展示）；**后端/DB/本地缓存持久化属于
Phase 5**（localCache 写回 + 截图），二期再做 DB 落库。

**验收**：`typecheck` ✅ · `lint` 0 error ✅ · vision.spec 26→31 ✅（alignVisionIndexes 3 条 +
消息 index 映射 1 条 + ocr 单图多行合并 1 条）· verify vision 7/7 ✅ · 全量 test 97 pass，
仅剩 env.server/getTweet 既有 4 fail 1 error（基线确认，与本改动无关）。

## DeepSeek 策略切到 openai-compatible + 结构化 AI 错误 toast

**背景**：用户把 DeepSeek Base URL 指向 OpenCode Go 端点时踩了两个坑——(1) URL 少 `v1` 段返回 404；(2) API Key 无效时返回 401，但前端 toast 只显示"请求失败，请检查网络"，无从排查。两个问题合并处理。

**改动一：provider 迁移（`app/lib/providers/deepseek.ts`）**

- `@ai-sdk/deepseek` → `@ai-sdk/openai-compatible`（`createOpenAICompatible({ name: 'deepseek', baseURL, apiKey })`）。
- 动机：OpenCode Zen/Go 与 DeepSeek 官方均为 OpenAI 兼容协议；旧 SDK 的 `thinking: { type }` 字段在第三方兼容端点上语义不确定。
- 思考强度：`minimal → 缺省`（不传 reasoning_effort）、`low/medium/high → high`、`max → max`。
- 关键补丁：OpenAI 兼容协议没有标准思考 off 开关，用 `transformRequestBody` 在 `reasoning_effort` 缺失时补发 `thinking: { type: 'disabled' }`，保留"不开启思考"语义。
- 测试：`provider-base-url.spec.ts` mock 改为 openai-compatible；`provider-strategy.spec.ts` 更新 buildProviderOptions 期望；新增 transformRequestBody 注入用例。

**改动二：结构化 AI 错误 toast**

- 服务端：新增 `app/lib/ai-error.ts` 的 `normalizeAIError()`——用 `APICallError` / `AISDKError` 判别，把 `url` / `statusCode` / `responseBody` / `isRetryable` / 解析出的 `providerMessage` 归整为可序列化的 `AITransportError`。三条路由（`ai-translation.ts` 的 tweet+IG、`ai-test.ts`）catch 里统一返回 `aiError` 字段，并把 `catch (error: any)` 收敛为 `unknown`。
- 前端：新增 `app/lib/ai-error-toast.tsx` 的 `toastAIError()` + `app/components/translation/AIErrorDetail.tsx`。有 `aiError` 时渲染结构化详情（HTTP 状态徽章 / 错误类型 / 端点 URL / 响应体预览），超时放宽到 8s；无结构化信息时退化为普通消息。
- 组件约束：toast 的 description 渲染在 `<p>` 容器内，`AIErrorDetail` 只用 span/code phrasing 元素 + CSS block 排版，避免 div/pre 内嵌 `<p>` 造成非法 HTML。
- 消费者：`use-translation-editor-logic`、`use-alt-translation-logic`、`IGTranslateDialog`、`AITranslationSettings`（测试连接）。
- 附带发现：`fetcher.ts` 拦截器对 `body.status !== 200` 一律 reject，导致 `handleTestConnection` 的 else 分支（展示 `data.cause`）实际是死代码，失败都走 catch——因此错误详情统一在 catch 里取 `aiError`。
- 测试：新增 `test/ai-error.spec.ts`（构造真实 `APICallError` / `AISDKError` 验证归一化）。

**验收**：`typecheck` ✅ · `lint` 0 error ✅ · 变更相关单测 34 pass ✅。注：`bun test` 全量 4 fail 1 error 为 `env.server` / `getTweet` 的环境相关既有失败，与本改动无关。

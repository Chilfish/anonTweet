## X Space 卡片接入（✅ 已完成）

**背景**：`/api/tweet/get` 实测对 Space 推文（`1968314084207788302`）不返回任何卡片 —— 其
`card.name = '3691233323:audiospace'` 的 `binding_values` 只有 `tweet_id` / `id` / `card_url`，
无标题无图片，被 `mapTwitterCard()` 的最终校验整个丢弃，页面只剩一个裸 `t.co` 链接。

**数据链**（先写临时探针脚本核实上游，再动手）：

- `TweetResultByRestId` → card `id` binding = Space id
- `AudioSpaceById`（queryId `HPEisOmj1epUNLCWTYhUWw`，`withReplays: true`）→
  `data.audioSpace.metadata` 提供全部卡片字段
- 实测对齐官方卡片：`2,478 人がリスニング/リプレイ` = `total_live_listeners(1245) + total_replay_watched(1233)`；
  `42:40` = `ended_at - started_at`；`9月17日` = `created_at`

**范围裁定（owner）**：**只做卡片 + 跳转 X 播放**。站内播放被否 —— 录音是 HLS，m3u8 响应头为
`Access-Control-Allow-Origin: https://x.com`（跨源取流被拦），站内播放需服务端媒体代理 +
`hls.js` 依赖 + 相应带宽，成本远超卡片本身。

1. **`creator_results` 是精简用户对象**：不含 `is_blue_verified` / `verified_type`，直接用会丢掉官方卡片上的

   而是 `undefined`），故一律以 `=== true` 收敛为布尔。
2. **不改 `parseTweet.ts`**：它是 Postmortem #001 的头号高危文件（10 次 fix），Space 识别放在异步层读原始
   `card`，保持解析器零改动。
3. **清理渲染噪音**：初版照搬官方 DOM，渲染了「主播」右对齐标签与 `affiliates_highlighted_label` 的 14px
   联合账号徽标；截图复核后两者都删（14px 下不可辨识的纯噪音），录音按钮底色也由 X 的冷灰 `#eff3f4`
   换成白（紫底上更干净）。
4. **临时探针脚本**（`tmp/probe-space.ts` 等）：用 `Requests` 运行时猴补丁注册临时资源，

## 边界态补全（✅ 已完成，同日追加）

初版只覆盖「已结束 + 可回放」。复核时由 owner 指出两类缺失，均补上并配 AC-SPACE-009/010：

**1. 可播放状态机**（`SpaceAvailability`，由 `state` + `is_space_available_for_replay` 推导）

| availability        | 条件                                   | 卡片表现                                           |
| ------------------- | -------------------------------------- | -------------------------------------------------- |
| `replayable`        | 已结束 + 回放开                        | 「播放录音」（唯一给播放入口的分支）               |
| `live` / `upcoming` | `Running` / `NotStarted`               | 「直播中」/「尚未开始」                            |
| `no-replay`         | 已结束但**未开启回放**                 | 「录音不可回放」，**不给**播放入口                 |
| `unavailable`       | 上游**无 metadata**（已删除/不可访问） | 中性墓碑条「Space 已删除或不可访问」+「在 X 查看」 |

关键取舍：没录音却摆「播放录音」= 把人送进播不了的页面；墓碑也不该用品牌紫大喊大叫（走 `bg-muted/40`）。

**2. 上游要区分「没有」与「取不到」**：已删除的 Space，`AudioSpaceById` 实测返回
`{ data: { audioSpace: { is_subscribed: false } } }`（节点在、metadata 无）；而请求失败
（429/网络）是抛错。**只有前者**渲染墓碑——否则会把限流误报成「已删除」；
后者不挂 `space`，正文链接照常渲染并记 `obsLog('space.fetch.failed')`。

**3. Space id 双通道识别**：实测推文 `1871586443388420240` **完全没有 card**，正文里只有一条
`x.com/i/spaces/1djGXroNWDExZ` 链接（该 Space 也已删除）——初版只认 card binding 的 id，
这类推文会被整条漏掉。改为 `resolveSpaceId(card, entities)`：优先卡片、回退正文 url 实体。

**踩坑（已复现的崩溃）**：`availability` 是后加字段，改动前落地的 `space`（memory LRU / 本地文件 /
DB jsonContent）没有它，组件直接 `ACTION_BY_AVAILABILITY[space.availability]` 拿到 `undefined`，
渲染时抛 `Cannot read properties of undefined (reading 'aria')`（dev 实测）。修法：
`resolveSpacePlaybackState()` 纯函数按早期就存在的 `isReplayAvailable` 回退推导，字段全缺时保守取
`no-replay`，并补回归测试（AC-SPACE-010）。

**验证**：上游 E2E 复核三条真实推文 —— 带卡片的已删除 Space（`2057046686871232598`）、
无卡片的已删除 Space（`1871586443388420240`）、已结束可回放（`1968314084207788302`），
availability 分别 `unavailable` / `unavailable` / `replayable`。

**4. 旧缓存回填（AC-SPACE-011，owner 复测指出）**：owner 实测「还是渲染了链接」——根因是
**缓存命中**：三条推文都从 NodeFS 命中改动前落库的旧结构（日志 `cache.get … hit:true`），
压根不会再走 `getEnrichedTweet`，于是新逻辑从未执行。

修法：在唯一读出口 `getLocalTweet()` 出口做一次回填/升级 —— 缓存不保留原始 `card`，但 Space
链接始终在实体里，`resolveSpaceId(null, entities)` 覆盖「带卡片 / 无卡片」两种推文；结果
best-effort 写回 localCache + DB（避免每次浏览重打上游）；取数失败保持原样，**不伪造墓碑**。
顺带把「`space` 存在但缺 `availability`」的旧结构也纳入自愈范围。

复测：`getLocalTweet` 对上述三条（全部 `hit:true`）现在分别返回 `unavailable` / `unavailable` /
带完整标题的卡片，二次读取仍为 `unavailable`。

**最终**：AC-SPACE 共 11 条；`typecheck` / `lint` / `verify --exit-on-fail`（448 passed）全绿。

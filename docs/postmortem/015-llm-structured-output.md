# Postmortem 015: LLM 结构化输出不可靠，靠多层防御兜底

- **日期**: 2026-09-18
- **严重级别**: SEV-2
- **分类**: 架构
- **状态**: Mitigated
- **根因归类**: 设计建模

## 摘要

把 LLM 当结构化 API 用会失败。AI 视觉上线当天的失败形态：describe 模式模型自造 index（`mediaIndexes: [0]` 却返回 `"index": 1`），UI 按图查找全部 miss；ocr 模式对一张图返回 10 条（按行拆分）；翻译步因为用的是 chat 模型，返回 `{"0": "译文"}` 而不是 `{"translations": [...]}`，直接抛 `NoObjectGeneratedError`。08-14 补齐到五层防线（反幻觉 prompt、索引映射注入、数量断言与重试、宽容解析、术语表与上下文注入）之后才稳定。

## 影响

- 用户可见：图片描述不显示、译文错位、调用直接 500。
- 返工：08-13 到 08-14 连续多轮加固。
- 隐藏风险：模型输出「看起来合理但错位」比直接报错更危险——UI 已经渲染，用户已经相信。

## 根因分析

1. 把 chat 模型当结构化 API 用。DeepSeek 是对话模型，严格的 `Output.object` 会失败；跨 provider 的结构化输出能力也不一致。
2. 模型会自造索引。代码用 `find(v => v.index === i)` 依赖模型回传正确的 index，而模型会顺手编一个，导致静默 miss。
3. 模型不遵守「一张图一条」。ocr 按行拆分，数量与图片数不符；`alignVisionIndexes` 在数量不一致时原样返回，上层又没有合并实现。
4. 失败不可见。解析失败被当成正常返回，直到 UI 什么都不显示才被发现。
5. 缺少上下文锚点。只用一句话 system prompt 加裸的 `tweet.text`，模型对图中无法辨认的名称只能瞎猜。

一句话归纳：LLM 的输出既不稳定也不自证，必须假设它会错位、会多给、会幻觉，用确定性代码兜底。

## 触发条件

更换 provider 或模型；图文数量不一致；图中出现知识库外的专有名词。

## 检测

人工测试发现（描述不显示、译文错位）。当时的盲区是解析失败没有结构化上报，只能靠人看 UI。

## 处置

从三层防御扩到五层：系统提示词写入反幻觉协议；把索引映射注入消息，数量匹配时用 `alignVisionIndexes` 强制重映射；新增 `VisionContentError` 与 `assertVisionResultCount`，数量不符时带反馈重试一次；用宽容解析（`parseOcrTranslation` + `extractJson`）替代严格 `Output.object`，空描述直接判为幻觉性失败；官方 alt 与术语表始终注入。

## 做得对的地方

OCR 与翻译两步解耦，是真实失败逼出来的正确产品决策（OCR 是提取、翻译是语义任务，可复用更便宜的文本模型）。用宽容解析而不是把用户卡在 `NoObjectGeneratedError`。用离线确定性 AC（假 key 真正调用 `runImageVision` 证明短路）覆盖，而不是只做源码扫描。

## 教训

不要把 LLM 当结构化 API。假设它会错位、多给、幻觉，用确定性校验加重试兜底，并让失败可观测。

# Postmortem 模板

每份报告按本模板写。元信息字段名与 `scripts/postmortem-check.ts` 的解析约定绑定，不要改名；`## Changed Files` 标题必须逐字一致。

## 元信息

```markdown
- **日期**: YYYY-MM-DD（首次记录日期）
- **严重级别**: SEV-0 ~ SEV-3（判据见 README「严重级别」）
- **分类**: 架构 / 流程 / 缺陷 / 依赖 / 变更
- **状态**: Active | Mitigated（定义见 README「状态」）
- **根因归类**: 设计建模 / 流程缺失 / 决策滞后 / 工具反馈
```

## 正文章节

1. **摘要** — 发生了什么、为什么、怎么补救，3~5 句。写系统条件，不写个人。
2. **影响** — 分用户可见、返工量、隐藏风险三块，能量化就量化。
3. **时间线** — 日期 + commit + 事件，按时间排序。回溯整理的报告如实标注「事后复盘」。
4. **根因分析** — blameless。列贡献因素，不要为了结论硬凑单一根因；必要时用 5 Whys。
5. **触发条件** — 潜伏缺陷被什么激活。
6. **检测** — 怎么发现的，当时的检测盲区在哪。
7. **处置** — 怎么止住、改了什么。
8. **做得对的地方** — 值得固化的行为。
9. **行动项** — 分缓解与预防，每条带负责人与完成判据。
10. **教训** — 1~2 句可执行结论，同步进 README「高频雷区」。
11. **## Changed Files** — 围栏代码块内每行一个受影响文件路径。
12. **关联报告** — 同源或复发的报告编号。

## 写作要求

- 不用 emoji。
- 不写「值得注意的是」「综上所述」这类填充。
- 区分事实与推测。查不到的写「未确认」，不要编造时间或数据。
- 行动项的负责人写实际归属；单人项目写「维护者」，不写「—」。
